# 整数筹码修复与完整手牌流水同步规格

日期：2026-10-24（Asia/Shanghai）

状态：待实施。基线：`d3de8d2`。配套计划：`docs/superpowers/plans/2026-10-24-money-hand-review-sync.md`。

## 1. 本轮范围

用户明确选择两个改动：

1. 修复 P1：新增金额输入可以把小数送入整数筹码引擎，导致分池派彩及下一手筹码不守恒。
2. 完整流水：整手结算后自动追加一条 `source=dz-pk`、`kind=hand_review` 的记录，供云端完整复盘。

保留已完成的训练设置、NPC 接入、本地最近 20 手、默认按需查看，以及默认关闭的“自动展开回顾”偏好。本轮的自动同步独立于查看偏好，取代原训练规格中“首版完整回顾仅本地保存”的范围约束。

其他评审发现的有效筹码计算、回顾边池报价、体验报告统计、听牌分类等不在本轮修复范围。不重跑原 A→F 训练改造，不部署，不改真实资金文件，不删除用户文件。

## 2. P1：阻断非法金额进入动作链

### 2.1 已确认反例

四人各买入 $200，总额 $800。UTG 弃牌，BTN 在新输入框手输加到 $6.5，两盲跟注，池 $19.5。公共牌皇家同花顺，三人平分：现有整数余筹算法派出 $20，剩余池变成 −$0.5；下一手清零该池后，总筹码多出 $0.5。

根因是 `src/components/GameTable.tsx` 的输入确认直接调用 `playerRaise`，`src/store/gameStore.ts` 也没有校验金额。`type=number`、`step/min/max` 不会替普通按钮点击执行表单校验。修复入口校验，继续沿用整数筹码和现有余筹分配规则。

### 2.2 UI 与 store 校验

- 手输金额保留原始字符串，确认前先检查非空/非空白，再转换。不能用 `Number('')` 把空输入当零。
- UI 只提交 `Number.isSafeInteger(value)`、大于零且处于当前合法金额区间的值。短码唯一合法全下目标仍可提交。
- 小数、负数、NaN、±Infinity、空输入、纯空白、超过安全整数范围的值拒绝；显示“请输入合法的整数筹码金额”或具体上下限，面板保留，不能执行动作。
- 不使用 `parseInt` 截断小数，也不自动四舍五入手输金额。快捷按钮仍按既有规则计算整数并展示最终执行金额，滑杆可加 `step=1` 作为辅助。
- `playerRaise` 在记录、日志或任何状态写入之前，至少拒绝非安全整数及负值；合法整数继续走现有最小加注、筹码上限、不完整全下和无再加注权限的归一语义。不要只保护 UI。
- 外部行动的 `src/act/applyAction.ts` 使用相同安全整数条件；无效金额返回 `bad_amount`，不能在 store 拒绝后仍报告执行成功。NPC 现有合法动作检查保持有效。
- 无效值前后筹码、pot、currentMaxBet、lastRaiseSize、当前玩家、decisionRevision、streetActions、liveHand.actions、gameLog 完全不变。

不通过修改派彩算法支持小数，不四舍五入现存底池、筹码、历史或资金来掩盖旧问题。如果发现已有异常数据，记录事实，不自动清空或改账。

### 2.3 金额验收

分别验证 UI 和直接 store 调用，不能只测一个共享校验函数。比较状态时深复制行动数组，避免原地修改使断言失效。

覆盖上述非法输入、合法普通加注、最小加注归一、超过筹码的上限归一、短码全下、没有重新开放加注权限。原 $6.5 反例必须在入口被拒绝；用合法 $6/$7 重跑公共牌三人平分，并补含死钱的整数余筹案例。结算及下一手始终守恒，所有新生成的筹码和底池均为非负安全整数，结算余池为 0。

## 3. hand_review：完整数据与记录格式

### 3.1 数据来源和完成时点

从已经生成的不可变 `CompletedHand` 构造记录，不解析 `gameLog` 或复制回顾组件的渲染文本。

使用 `handleShowdown.finish` 中已支付结果的归档事件，或订阅完成历史新增项；不能仅订阅 `stage === 'showdown'`，当前游戏会先切阶段再支付。最后一次 NPC 行动的同步上下文必须已经在动作中。

上传完整事实：

| 内容 | 必须保留 |
| --- | --- |
| 手身份与配置 | version/id/sessionId/handNumber、起止时间、本手按钮、盲注、买入深度/金额、场景和对手配置 |
| 玩家与底牌 | 各座位身份、位置、风格、盲注前筹码、真实底牌，包括已弃牌的 NPC |
| 实际行动 | 全部 actionSeq、actorId、街、公共牌快照、potBefore、currentBetBefore、currentMaxBetBefore、callCost、amountAdded、raiseTo、raiseIncrement、allIn |
| NPC 依据 | 实际动作的 turnToken/actorId、reasonCode/profileId、position/handKey、priceTier/stackDepth、samples/equity/evReference、assumptions/fallback/rngDraw；无依据时保留 null |
| 结算 | 实际公共牌、各层派彩和退款、初末筹码及净变化、endKind |

不上传 deck、未发出的转河牌、进行中 liveHand、未执行/过期任务的诊断；不补造 NPC 原因，不用真实对手牌重新算一个结果冒充当时的估计。JSON 的 null/空数组和浮点权益估计正常保留。

### 3.2 沿用记录库接口，适配大小限制

已核对本地 `sqlite-lib/recordstore/validate.py` 及接口测试：

- 自定义 `hand_review` 类型合法，不需要登记新 kind 或修改数据库。
- POST `/v1/records` 首次创建返回 201；相同 client_key 返回 200 和原记录。
- `body` 上限 64 KiB，`payload` 上限只有 16 KiB，按 UTF-8 字节数计算。不能直接把一个可能超限的完整档案塞入 payload。

首版协议如下：

| 字段 | 固定口径 |
| --- | --- |
| source | `dz-pk` |
| kind | `hand_review` |
| client_key | `dz-pk:hand_review:{sessionId}:{handNumber}`，与 game_log 命名空间分开 |
| created_at | 已完成档案的 endedAt，UTC；重试时保持不变 |
| body | 简短中文摘要 + 一个完整紧凑 JSON 代码段，JSON 内容就是 CompletedHand |
| payload | 仅索引与版本：schema_version=1、hand_id、session、hand、table、stage=showdown、scenario、buy_in_bb、human_net、snapshot_format=`completed-hand-json/v1`、snapshot_location=`body` |

body 固定为中文摘要、空行、JSON代码段。代码段以三个反引号加json开始，以三个反引号结束；段内是 `JSON.stringify(completedHand)` 的完整紧凑结果，不添加省略号。摘要只描述第几手、级别/买入、底牌与结果，不从当前 UI 拼接尚未完成的信息。

提供纯函数构造和读取该记录，测试从 body 提取 JSON 后与原 CompletedHand 深度相等。消费者可通过 `source=dz-pk&kind=hand_review` 查流水，按 session + hand 关联既有 game_log；牌局顺序以手编号和 actionSeq 为准，不依赖上传到达顺序。

构造前校验必要结构与字段，不能仅依赖当前宽松的 `isCompletedHand`。对已有完整历史保留原数值；旧小数或净变化异常可附完整性说明，不能为了上传改账。无完整底牌/动作的旧文本流水不能伪造快照。

测量典型和高行动数手牌的 body/payload UTF-8 大小。超出接口限制时保留本地完整档案及失败状态，给出明确原因；不能截掉底牌、动作、assumptions 或结算后假装“完整”，也不能把已知 413 条目放入无限重试。首版不新增分片协议或改记录库上限。

## 4. 同步、去重与失败恢复

### 4.1 同步范围

- 新完成手牌自动入队，不要求打开回顾，也不依赖自动展开开关。
- 启动时等待历史 store 完成 hydration，再对本地已有最近 20 手中的完整档案补传，使用相同 client_key 去重；可用 `persist.onFinishHydration` 加已恢复检查，注册和执行均幂等，不能恢复前读到空数组就结束。只读取真实档案，不从旧日志猜底牌；历史补传不触发回顾弹窗。
- 最近 20 手是查看上限；待上传队列独立持有完整快照。离线产生超过 20 手时，旧待上传项不能随展示历史被淘汰。
- 入队时深复制并固定请求内容。下一手、离桌、改配置、切会话和重试不能改变已入队快照或标识。

### 4.2 最小实现建议

新增独立 `handReviewSync` 和持久 outbox，复用既有同源接口与记录字段。默认不改旧 game_log 线协议/队列；同步初始化放入 main，保证只注册一次。

状态至少区分待同步、已同步、失败；成功保留记录库 id/手标识供核对。界面可在最近手牌或回顾处显示简洁状态、待同步数量和失败后的重试入口，不要求用户再批准每手上传。

- 先保存待发快照，再发 HTTP；游戏结算不等待请求。离桌、关闭回顾和发下一手不能清队列。
- 网络异常、超时、5xx、408/429 保留待发项，按有界等待重试；可沿用约60秒重试和启动重试。单次请求有超时，不能永久卡在 fetching。
- 400/413 等确定性错误转失败状态并保留全文，不让一个坏条目永久阻塞后续手牌。手动重试仍使用原 key。
- 只有确认201/200且返回JSON记录的 source/kind、`record.payload.hand_id` 相符，body中还原的完整档案与待发档案一致，才标成功并移除待发项。返回记录顶层没有hand_id，也不回传client_key。内容不符时保留失败原因，不另造key绕过去重。请求落库但响应丢失时重试，相同key不能创建第二条。
- outbox 写入不可用时保留本次会话内存队列，显示无法持久化的状态；不能把未落库当成功，也不能阻塞牌局或修改资金。

### 4.3 并发与重复事件

不能照搬旧 `logSync.flush` 的旧快照覆盖模式：A 请求期间若 B 入队，A 成功后按旧数组 `slice(1)` 写回会丢 B。每次确认只从**当前队列**按 key 移除已成功的项，保留期间新加入的记录；每个页面flush单实例，重复入队去重。

持久outbox应按client_key原子写入/删除，优先使用IndexedDB。若沿用localStorage整数组，必须有跨标签锁及锁内读最新后更新的等价保证；单页面“先读最新再写”不能防止两个标签互相覆盖。存储或锁能力不可用时按上节回退内存并明确提示，不能宣称待发项已持久化。

重复归档、store 重渲染、刷新补传、多个入口初始化或多标签请求，靠客户端队列去重与服务端 client_key 幂等处理。相同手牌跨会话编号重用时仍是不同记录。

持久的成功标记可以减少重复请求；加载/迁移失败时不能无故清空原待发数据。日志只输出手标识、数量、状态码和错误原因，不打印完整底牌、body、payload、服务地址或凭证。

## 5. 验收与边界

1. 非法金额从 UI/store/API 三个入口都不执行，原筹码反例被阻断，合法整数分池/下一手守恒。
2. 全弃赢池、翻牌弃牌、多人摊牌、全下/边池的完整档案均产生 hand_review；最后一次 NPC 依据、已弃牌底牌和实际结算结果完整保留。
3. 本人弃牌但其余玩家仍行动、进行中退出，不发送未完成档案；未发公共牌保持空白。
4. 默认关闭自动展开仍上传；开启/关闭/手动看回顾都不会改变请求内容或重复上传。
5. 断网→入队→离桌/刷新→恢复成功；重复事件及丢响应重试只落一条；A发送期间B入队及多标签并发不丢记录；离线超过20手不丢待发项；400/413失败不堵后续。
6. 本地已有20手在hydration后可补传，后续重复启动不增加重复记录；从流水body还原的完整JSON与原始档案一致，错误的200/201回包不能标成功。
7. 测试/试玩使用fetch、浏览器存储和资金接口替身或隔离临时数据库；不得写真实流水或资金。验证真实接口契约时只用隔离记录库，不部署、不改库模型。
8. 跑相关及全量测试、构建、lint，记录已知旧错误与新增情况；更新计划并本地提交。

这份规格的完成标准是输入守恒与真实完整快照可可靠入队/落库，不以生成了日志字符串或HTTP请求发出就宣布同步成功。
